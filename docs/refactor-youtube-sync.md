# YoutubeVideoAnalyzer 리팩토링 요구사항 정의서

> 초기 설계 자료다. 최종 정책과 문서별 적용 순서는 [문서 안내](youtube-analysis-refactoring.md)를 따른다. 현재 구현 완료를 의미하지 않는다.

## 1. 목적

`eightjbbm.keepgo.interestextraction.service.youtubeanalyzev3.DefaultYoutubeVideoAnalyzer#analyze`를 리팩토링한다.

`List<Video>`에서 장소(`OutingPlace`)와 행사(`OutingEvent`)인 `OutingGuide`를 추출하고, 기존 분석 결과와 통합하여 반환한다.

## 2. 데이터 관계 및 동일성

- 하나의 영상에서 여러 Guide가 추출될 수 있고, 하나의 Guide가 여러 영상에서 추출될 수 있다.
- `VideoAnalysis`와 추출된 모든 Guide를 `VideoAnalysisResult`로 연결한다.
- `(videoAnalysisId, outingGuideId)` 복합키로 동일 매핑의 중복을 방지한다.
- 유형(Place/Event), 이름, 도로명주소로 구성된 `GuideKey`를 동일성 판단 기준으로 사용한다. Place와 Event 사이의 동일성은 인정하지 않는다.
- 행사 기간과 회차는 식별에 포함하지 않는다. 같은 이름·주소의 반복 행사는 동일한 Event로 취급한다.
- 이름과 주소는 초기 입력값을 그대로 사용한다. 공백 제거, 대소문자 변환, 유니코드 정규화를 수행하지 않는다.
- 공통 `OutingGuide` 테이블에 유형·이름·도로명주소의 복합 유일성 제약을 적용한다. 키 구성 필드는 `NOT NULL`로 저장한다.
- 동일 키의 Guide가 존재하면 설명, 좌표, 행사 기간을 포함한 기존 필드를 보존하고 해당 Guide를 재사용한다.
- 메모리 비교, DB 제약 및 `isSameAs`의 동일성 규칙을 일치시킨다. 기존 중복 데이터의 참조와 매핑을 대표 Guide로 이관한 후 제약을 적용한다.

### MySQL과 Java의 문자열 동일성

- Java의 `GuideKey.equals` 및 `isSameAs`는 문자열에 `String.equals`를 사용하고, `hashCode`도 같은 필드로 구성한다. Spring에서 별도의 문자열 정규화나 무시 비교를 적용하지 않는다.
- MySQL의 이름·도로명주소 컬럼은 `VARCHAR`, 문자 집합은 `utf8mb4`, collation은 `utf8mb4_0900_bin`을 사용한다. 이 collation을 지원하는 MySQL 8.0.17 이상인지 실제 운영 버전을 확인한다.
- `utf8mb4_0900_bin`은 대소문자와 유니코드 코드 포인트의 차이를 구분하고 `NO PAD` 속성으로 후행 공백도 구분한다. `utf8mb4_bin`은 `PAD SPACE`이므로 대체재로 사용하지 않는다.
- 유효한 유니코드 입력이 저장·조회 중 손실 없이 왕복하도록 연결 문자 집합도 `utf8mb4`로 맞춘다. 조회 쿼리에서 `LOWER`, `TRIM` 또는 다른 collation으로 동일성 규칙을 변경하지 않는다.
- 배포 전 운영 버전과 컬럼 정의를 확인하고, 대소문자·후행 공백·유니코드 조합 형태가 다른 문자열의 Java 비교, DB 조회 및 유일성 제약 결과가 일치하는지 검증한다. 미지원 버전에서는 동등한 비교를 보장하는 대안을 별도로 확정한다.
- 근거: [MySQL Unicode Character Sets](https://dev.mysql.com/doc/refman/8.0/en/charset-unicode-sets.html), [MySQL binary 및 _bin 비교](https://dev.mysql.com/doc/refman/8.0/en/charset-binary-collations.html).

## 3. 분석 이력 재사용

- 영상별 최신 분석 이력만 참조한다. 최신 기준은 생성 시각과 ID로 결정한다.
- 진행 중이거나 재실행 대기 중인 작업이 있으면 Singleflight로 해당 작업을 공유한다. 공유한 작업이 최종 실패해도 같은 호출 안에서 새 분석을 반복 생성하지 않는다.
- 활성 작업이 없으면 최신 완료 이력의 상태에 따라 다음과 같이 처리한다. 과거의 더 오래된 성공 이력으로 대체하지 않는다.

| 최신 완료 이력 | 처리 |
|---|---|
| `SUCCESS` | `VideoAnalysisResult`의 모든 Guide를 재사용하며 기존 결과를 변경하지 않음 |
| `NOT_FOUND` | 추출할 장소·행사가 없는 영상으로 간주하여 분석 대상에서 제외하고 빈 결과 사용 |
| `FAILED` | 후속 요청에서 신규 분석 대상에 포함 |
| 이력 없음 | 신규 분석 대상에 포함 |

- 완료 이력은 모두 판단에 사용하지만, `FAILED`의 실패 결과를 추출 결과로 재사용하지는 않는다.
- `FAILED`를 후속 요청에서 다시 분석할 때는 기존 실패 이력을 보존하고 새로운 `VideoAnalysis`를 생성한다. 이는 동일 작업 안의 호출 재시도·소유권 인계와 구분한다.
- 영상별 최신 이력의 일괄 조회와 관련 인덱스를 지원한다.

## 4. 배치 및 병렬 분석

- 신규 분석 대상의 영상 ID를 최대 10개씩 분할한다.
- 입력 영상 ID의 중복을 제거하고, 영상별 신규 작업 등록에 성공한 대상만 새 배치에 편성한다.
- 메서드에 전달하는 전체 영상 수에는 별도 상한을 두지 않는다. 최대 10개는 AI 호출 한 번의 배치 크기이다.
- 각 신규 배치의 영상별 활성 등록, `VideoAnalysis` 생성, 배치 생성 및 소속 연결은 하나의 짧은 DB 트랜잭션으로 처리한다. 일부 영상의 등록 경쟁에서 진 경우 해당 영상은 기존 작업을 공유한다.
- 실행기 제출은 등록 트랜잭션 커밋 이후 수행한다. 커밋 후 제출 전에 프로세스가 종료되어도 저장된 `PENDING` 배치를 후속 요청이 실행할 수 있어야 한다.
- 각 배치는 `AiServerService#analyzeVideoV2`로 병렬 분석한다.
- 영상별 상태는 `AnalyzeVideoResponseV2.Success.Result#status`로 판단한다.
- 동일 영상에서 추출된 여러 Guide를 모두 수집한다.
- **Scatter-Gather** 패턴으로 배치를 독립 처리하고 결과를 통합한다.
- 호출에서 시작된 분석은 애플리케이션이 관리하는 실행 범위에서 수행하며, Producer-Consumer 구조를 전제하지 않는다.
- 호출자의 연결 종료나 대기 취소는 이미 시작된 작업을 취소하지 않는다. 분석과 생존 신호 갱신은 계속 수행한다.
- 논리적 배치의 실행 수명은 최초 등록부터 **10분**으로 설정한다. 대기·호출·재시도·소유권 인계 시간을 포함하며 인계로 기한을 연장하지 않는다. 이 값은 설정 가능하게 한다.
- 실행 기한은 결과 저장 트랜잭션에서 배치 잠금을 확보한 후 소유권·실행 버전과 함께 검증한다. 기한 내 검증에 성공하면 유한한 DB 타임아웃 안에서 기한 이후 커밋도 허용한다. 결과 저장과 기한 초과 종료는 같은 배치 잠금으로 직렬화한다.
- 기한 내 저장 검증을 통과하지 못한 미완료 배치는 실행권을 무효화하고 소속 미완료 분석을 `FAILED / EXECUTION_DEADLINE_EXCEEDED`로 종료한다. 이후 도착한 응답은 저장하지 않는다.
- 등록 시각, 실행 기한, 소유권 만료 판정은 DB 시간을 공통 기준으로 사용한다.
- 프로세스 종료 시 실행 지속을 보장하지 않는다. 후속 요청이 만료 작업을 복구하되, 10분 기한까지 지난 작업은 최종 실패 처리한다.
- 최대 병렬 실행 배치 수는 설정 가능하게 한다. 실행 용량이 부족하면 배치를 DB의 `PENDING` 상태로 유지하고, 슬롯이 생기면 애플리케이션 실행기가 실행권을 원자적으로 확보하여 시작한다. 대기 배치를 모두 실행기 메모리 큐에 제출할 필요는 없다.
- 대기 시간도 최초 등록부터 10분에 포함한다. 실행 전 기한이 지난 배치는 AI를 호출하지 않고 최종 실패 처리한다. 기존 작업 공유와 완료 결과 재사용은 신규 AI 실행 슬롯을 소비하지 않는다.
- 애플리케이션 실행기는 대기 배치 실행과 기한 초과 처리를 담당하며, 호출자의 연결 종료에도 동작한다. 프로세스 종료 후에는 후속 요청이 미완료 배치를 확인하여 실행 또는 종료 처리를 재개한다.
- 실행 수명은 전체 결과의 저장·반환 시간을 무제한 보장한다는 의미가 아니며, DB 작업에도 유한한 타임아웃을 적용한다.

## 5. 배치별 트랜잭션

AI 응답 수신 후 다음 작업을 배치별 하나의 DB 트랜잭션으로 수행한다.

- 현재 작업의 소유권 및 실행 버전 검증
- 배치 내부의 `GuideKey` 중복 제거
- 기존 Guide 재사용 및 신규 Guide 저장
- 모든 추출 Guide의 `VideoAnalysisResult` 저장
- 모든 영상의 분석 상태 및 완료 정보 저장
- 배치 완료 상태 저장
- 신규 Guide의 임베딩 요청을 Outbox에 기록

각 배치는 독립적으로 커밋하며, 저장 작업은 모두 성공하거나 모두 롤백되어야 한다. AI 호출 자체는 DB 트랜잭션에 포함하지 않는다.

- 배치 잠금 확보 후 소유권·실행 버전·실행 기한을 검증하고 커밋까지 동시 인계와 최종 종료를 차단한다.
- 여러 Guide는 모든 배치에서 동일한 `GuideKey` 정렬 순서로 저장하여 잠금 순서 역전에 의한 교착상태를 줄인다. 정렬 순서는 유형·이름·주소를 기준으로 명시적으로 고정한다.
- 교착상태로 롤백되면 이미 받은 AI 응답을 유지하고, 새 트랜잭션에서 배치 저장 전체를 제한적으로 재시도한다. 매번 소유권·실행 버전·실행 기한을 다시 검증하며, 실행권을 잃거나 기한을 넘으면 저장을 중단한다.

## 6. 중복 및 동시 저장

**멱등 처리(Idempotent Receiver)** 원칙을 적용한다.

- DB 유일성 제약과 원자적 upsert 또는 동등한 충돌 처리로 중복 Guide 생성을 방지한다.
- 충돌 처리는 기존 Guide의 필드를 덮어쓰지 않고 기존 ID를 확보하는 방식으로 수행한다.
- 같은 Guide를 추출한 모든 분석은 동일한 Guide에 연결한다.
- 전체 결과의 중복 제거는 반환 시 수행하며, 배치별 저장의 선행 조건으로 두지 않는다.

## 7. 상태 및 실행 이력

| 구분 | 상태 |
|---|---|
| 배치 실행 | `PENDING`, `IN_PROGRESS`, `COMPLETED`, `FAILED` |
| 영상별 분석 | `IN_PROGRESS`, `SUCCESS`, `NOT_FOUND`, `FAILED` |

- 배치에는 소속 영상, 실행 버전, 소유권 정보, 생존 신호 시각, 호출 시도 횟수, 다음 재시도 시각 및 실패 정보를 기록한다.
- `VideoAnalysis`에는 생성·완료 시각과 실패 코드·사유를 기록한다.
- 배치의 `COMPLETED`는 유효한 응답의 영상별 결과가 모두 저장된 상태이다. 영상별 실패가 포함되어도 배치는 완료될 수 있다.
- 호출 재시도와 소유권 인계 시 동일한 논리적 배치·분석 이력을 유지하고, 실행 버전으로 작업자를 구분한다.
- 단순 재실행이나 소유권 인계로 호출 재시도 횟수를 초기화하지 않는다.
- 완료된 `VideoAnalysis`와 `VideoAnalysisResult`는 변경하지 않는다. 진행 중 작업의 상태·소유권·시도 횟수는 갱신할 수 있다.
- 최종 실패 후 후속 요청에서 시작하는 새 분석은 별개의 논리적 작업이며, 자체 호출 예산과 10분 실행 수명을 갖는다.
- 배치 최종 실패 시 소속 미완료 `VideoAnalysis`를 모두 `FAILED`로 종료하고 완료 시각·실패 사유를 기록한다. 배치 종료, 영상별 종료, 해당 작업의 활성 등록 해제를 하나의 트랜잭션에서 처리한다.
- 결과가 확정된 영상별 이력은 후속 종료 처리에서 다시 변경하지 않는다. DB 장애로 종료 처리를 저장하지 못했다면 후속 복구에서도 동일한 원자적 종료 절차를 적용한다.

## 8. Singleflight 및 만료 복구

- 영상 ID 기준으로 진행 중인 작업을 공유하여, 배치 구성이 달라도 동일 영상을 중복 실행하지 않는다.
- 활성 작업 조회, 완료 이력 확인, 영상별 신규 작업 등록 사이의 경쟁을 제어한다. 영상별 활성 작업의 유일성을 DB에서 보장한다.
- 등록 충돌 후에는 활성 작업과 최신 완료 이력을 다시 조회한다. 활성 작업이 있으면 합류하고, 충돌했던 작업이 이미 완료됐다면 그 작업의 확정 결과를 사용한다. 완료 이력을 반영하지 않은 오래된 판단으로 신규 분석을 생성하지 않는다.
- 합류한 작업의 배치 ID와 분석 이력 ID를 유지하여 자신이 기다린 작업의 결과를 조회한다. 다른 요청이 이후 생성한 분석 이력으로 대상을 바꾸지 않는다.
- 예를 들어 요청 A가 `[영상1, 영상2]`, 요청 B가 `[영상2, 영상3]`을 동시에 처리하면 영상2는 하나의 작업에만 등록된다. 다른 요청은 해당 작업을 공유하고 각자 확보한 나머지 영상만 새 배치에 편성한다.
- 후속 요청은 해당 영상이 속한 배치의 재시도와 결과 저장 완료까지 기다린다.
- 실행권 획득과 실행 버전 증가는 원자적으로 처리한다.
- 실행 중인 작업은 생존 신호로 소유권을 갱신한다. 초기값은 **10초마다 갱신, 마지막 갱신부터 60초간 유효**로 설정한다.
- 후속 요청은 실행 기한이 남은 소유권 만료 배치를 확인하여 `PENDING`으로 전환하고 이전 실행권을 무효화한 뒤 재실행할 수 있다. 기한이 지났다면 재실행하지 않고 최종 종료 절차를 적용한다.
- `PENDING`은 실행 가능한 대기 상태이며, 자체적으로 만료를 판단하거나 실행하지 않는다.
- 소유권을 잃은 작업자의 늦은 결과는 저장 트랜잭션에서 거부한다.
- 생존 신호, 실패 기록, 완료 처리 및 활성 등록 해제도 소유권·실행 버전 조건으로 보호하여 이전 작업자가 새 소유자의 상태를 덮어쓰지 못하게 한다.
- 소유권 검증은 중복 결과 저장을 방지한다. 이미 전송된 외부 AI 호출은 인계 시 중첩될 수 있으며, 외부 호출 자체의 정확히 한 번 실행을 보장하지 않는다.
- 완료·최종 실패 시 진행 중 등록을 해제한다.
- 다중 인스턴스에서도 동일한 소유권 규칙을 적용한다.

## 9. 추출 데이터 검증

- 정상 반환된 AI 응답은 요청 영상 ID와 정확히 대응하며, ID 누락·중복·미요청 ID 없이 영상별 상태와 필수 필드가 응답 계약을 만족한다고 가정한다.
- 응답 구조의 유효성과 Guide의 저장 가능성은 구분한다. 응답 계약상 허용되는 주소 누락은 아래 도메인 검증을 적용한다.
- 도로명주소가 없거나 공백인 결과는 Guide 저장·반환·임베딩에서 제외한다.
- 제외 사유는 분석 이력에 기록한다.
- 유효한 Guide가 함께 추출되었다면 해당 Guide는 정상 저장한다.
- 모든 추출 결과가 주소 누락으로 제외되면 해당 영상은 `FAILED / INVALID_GUIDE_DATA`로 기록한다.
- 데이터 검증 실패는 AI 호출의 즉시 재시도 대상으로 삼지 않는다.

## 10. 임베딩

**Transactional Outbox** 패턴을 적용한다.

- 신규 생성된 Guide만 임베딩 대상으로 기록한다.
- 별도 처리기가 커밋된 요청을 읽어 `AiServerService#embedPlaces`를 호출한다.
- Place/Event 구분 없이 처리하며, 중복 호출에도 안전해야 한다.
- 임베딩 실패는 저장된 분석 결과와 반환에 영향을 주지 않는다.
- 임베딩 누락·최종 실패 작업의 운영 재처리는 별도 책임으로 두며, 이 메서드는 기존 Guide를 다시 임베딩하지 않는다.

## 11. 실패 및 재시도

| 상황 | 처리 |
|---|---|
| 정상 응답에 영상별 성공·실패 혼재 | 모든 영상의 상태와 추출 결과를 함께 저장 |
| AI 호출 실패·타임아웃 | 재시도 가능한 오류이면 재시도, 소진 시 배치 실패 |
| 결과 저장 실패 | 해당 배치 전체 롤백 후 별도 실패 기록 |
| 저장 중 교착상태 | AI 재호출 없이 저장 트랜잭션 전체만 제한적으로 재시도 |
| 소유권 만료 | 이전 실행권 무효화 후 `PENDING`으로 전환 |
| 일부 배치 실패 | 다른 배치의 커밋 결과 유지 및 부분 결과 반환 |
| 임베딩 재시도 소진 | 실패 상태 보존, 분석 결과 유지 |
| 실행 수명 10분 초과 | 실행권 무효화 및 미완료 분석 최종 실패 |
| 정상 응답의 영상별 `FAILED` | 해당 실패를 저장하고, 후속 요청에서 신규 분석 대상으로 판단 |

- AI 분석과 임베딩은 최초 호출 이후 최대 3회 재시도한다. 총 호출은 최대 4회이다.
- 기본 간격은 **1초 → 2초 → 4초**, 각 간격에 ±20% jitter를 적용한다.
- `Retry-After`가 제공되면 해당 시간을 우선한다.
- 영구적 오류는 재시도하지 않는다.
- AI 분석은 배치 단위, 임베딩은 Outbox 작업 단위로 재시도한다.
- 재시도는 한 계층에서 관리한다.
- 영상별 실패는 동일 호출 안에서 별도 즉시 재분석하지 않는다. 후속 요청의 최신 이력이 `FAILED`이면 새 분석을 시작한다.
- AI 호출 타임아웃은 소유권 만료와 별도로 설정하며 남은 실행 수명을 넘지 않게 한다. 재시도 대기(`Retry-After` 포함)도 실행 기한을 연장하지 않는다.
- 호출 시도 횟수는 전송 전에 소유권·실행 버전 검증과 함께 원자적으로 기록한다. 전송 여부가 불확실한 시도도 예산에 포함하여 인계로 호출 예산이 늘어나지 않게 한다.
- 저장 교착상태 재시도 횟수와 대기 간격은 설정 가능하게 하고 AI 호출 재시도 예산과 분리한다. 전체 실행 기한은 연장하지 않는다.
- 교착상태 재시도 소진 또는 그 외 결과 저장 실패는 배치 전체 롤백 후 별도 트랜잭션의 최종 실패 처리로 종료한다. 저장 실패만을 이유로 AI를 즉시 재호출하지 않는다.
- 실패 기록은 결과 저장 트랜잭션이 롤백되어도 남아야 한다.
- DB 장애로 실패 기록도 남길 수 없으면 운영 로그에 기록하고, 후속 요청에서 소유권 만료 및 실행 기한을 기준으로 복구한다.
- 재시도 및 생존 신호 관련 값은 설정 가능하게 한다.

## 12. 반환

- 재사용 결과와 성공적으로 저장된 배치의 추출 결과를 통합한다.
- `GuideKey` 기준으로 중복을 제거하며 순서는 보장하지 않는다.
- 반환형은 `List<OutingGuide>`로 한다. 실패 배치나 영상별 상세 상태는 반환에 포함하지 않는다.
- 일부 배치가 실패하면 저장된 성공 결과를 반환하고, 반환할 Guide가 없으면 빈 목록을 반환한다.
- 정상 미추출과 분석 실패의 구분, 상세 실패 정보 확인 및 후속 처리의 책임은 상위 로직에 둔다. 해당 로직은 저장된 분석 이력을 확인한다.
- 특정 호출의 결과를 추적할 수 있도록 내부 실행 컨텍스트와 로그에 해당 호출이 생성·공유·재사용한 배치 ID 및 분석 이력 ID를 남긴다. 상위 로직이 특정 실행을 확인할 때는 단순 최신 조회 대신 해당 ID를 사용하며, 반환형은 변경하지 않는다.
- 임베딩 완료를 기다리지 않는다.

## 13. 주요 인수 조건

- 동일 키라도 Place와 Event는 별개로 저장되며, 같은 유형·이름·주소의 Guide는 기존 필드를 보존한다.
- Java와 MySQL에서 대소문자·후행 공백·유니코드 조합 형태의 차이를 동일하게 구분한다.
- 겹치는 영상이 포함된 동시 요청에서 영상별 활성 작업은 하나만 등록되고 다른 요청은 공유한다.
- `SUCCESS`는 기존 Guide를 반환하고 `NOT_FOUND`는 AI를 호출하지 않으며, `FAILED`는 후속 요청에서 새 이력으로 분석한다.
- 소유권 인계 전 작업자의 늦은 응답·실패 기록·생존 신호는 새 작업자의 상태를 변경하지 못한다.
- 연결 종료 후에도 분석이 지속되며, 논리적 배치는 최초 등록부터 10분 기한을 적용한다.
- 저장 중 실패하면 해당 배치의 Guide·매핑·완료 상태·Outbox 기록은 함께 롤백되고 다른 배치의 커밋은 유지된다.
- 정상 응답의 영상별 실패는 이력에 저장되며 동일 호출에서 즉시 재분석하지 않는다.
- 영상별 활성 등록·분석 이력·배치 소속은 함께 커밋되거나 함께 롤백된다. 커밋 후 실행기 제출 전에 종료되어도 후속 요청으로 `PENDING` 작업을 복구할 수 있다.
- 등록 충돌 직후 기존 작업이 완료되고 활성 등록이 해제되어도, 요청은 해당 완료 결과를 사용하고 불필요한 신규 분석을 생성하지 않는다.
- 실행 용량 부족 시 `PENDING`으로 대기하고 슬롯 확보 후 실행한다. 대기 중 10분 기한이 지나면 AI 호출 없이 최종 실패 처리한다.
- 기한 내 배치 잠금 확보 및 저장 검증에 성공한 트랜잭션은 DB 타임아웃 안에서 커밋할 수 있다. 경쟁하는 기한 초과 처리는 성공 결과를 실패로 덮어쓰지 못한다.
- 배치 최종 실패 시 소속 미완료 분석과 활성 등록이 원자적으로 종료되어, 후속 요청이 종료된 작업을 계속 기다리지 않는다.
- 저장 교착상태 재시도는 AI를 다시 호출하지 않으며, 새 트랜잭션에서 전체 저장과 실행권 검증을 다시 수행한다.
- 같은 Outbox 작업을 중복 전달해도 임베딩 결과가 중복 생성되지 않는다.
- 특정 호출의 작업 ID를 통해 후속 요청의 새 분석과 구분하여 결과를 추적할 수 있다.

## 14. 운영 관측

- 활성 작업 수, `PENDING` 배치 수와 대기 시간, 기한 초과 수, 소유권 인계 수, AI 호출·재시도 횟수, 저장 교착상태·재시도 횟수, Outbox 최종 실패 수를 관측한다.
- 로그에는 배치 ID, 분석 이력 ID, 실행 버전 및 실패 코드를 포함하여 생성·공유·인계·완료·실패 흐름을 추적할 수 있게 한다.
