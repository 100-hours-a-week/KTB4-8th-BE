# 영상 분석 메시지 브로커의 도입 요구사항과 비교 기준을 정한다

2026-11-02 논의에서 YouTube 영상 분석에 메시지 브로커를 도입할 이유와 검증할 가설을 합의했다. 이 ADR은 향후 검토의 기준을 기록하며, 브로커 도입이나 제품 선택을 승인하지 않는다. 현재의 코드·설정·AI 계약을 변경하지 않으며 [ADR 0003](0003-in-process-analysis-mysql-coordination.md)과 [ADR 0004](0004-shared-video-analysis-results.md)를 대체하지 않는다. 아래 구조와 동작은 현행 구현이 아닌 검토안이다.

## 배경과 도입 목적

검토 범위는 YouTube 영상 분석이며 채팅·코스 추천·임베딩은 제외한다. 사용자는 현재 요청에서 결과를 기다리고, 전체 완료 기한을 넘으면 실패 응답을 받는다. 접수만 알리고 나중에 결과를 제공하는 사용자 흐름으로 바꾸지는 않는다.

첫 번째 목적은 API 서버와 AI 실행 구조 사이의 결합을 줄이는 것이다. API 서버는 AI 인스턴스의 주소·개수·개별 실행 용량을 관리하지 않고 공통 계약으로 작업을 발행한다. AI 인스턴스별 백엔드 워커가 HTTP 호출 어댑터를 맡고 AI 인스턴스와 함께 증설·축소된다. AI 배치 구조의 변경이 API 서버의 코드·설정 변경으로 이어지지 않는 것을 목표로 한다. 메시지·결과 형식, 분석 식별자와 완료 기한에 관한 계약은 공유한다.

두 번째 목적은 AI 실행 용량에 맞춰 작업 전달을 제어하는 것이다. 여기서 처리량 제어는 우선 초당 요청 수가 아니라 인스턴스별 동시 분석 수의 제한을 뜻한다. 브로커가 AI 용량을 자동으로 발견하는 것은 요구하지 않는다. 운영 설정으로 인스턴스별 한도를 선언하고 브로커가 전달 한도를 집행하며, 워커는 호출과 ACK의 수명을 연결한다.

## 검토 구조와 책임

```text
백엔드 API → 공용 작업 큐 → [백엔드 워커 ↔ 대응 AI 인스턴스] × N
                              ↓
                          결과 DB 저장
                              ↓
                          완료 알림 발행 → 대기 중인 API 요청
```

- 각 워커는 대응하는 AI 인스턴스 하나만 호출하며, 둘의 대응 관계를 배포 단위로 보장한다.
- 인스턴스별 실행 한도 C를 소비 설정에 반영한다. 워커는 전달받은 작업을 무제한 내부 실행 큐로 넘기지 않는다.
- 워커는 분석이 끝나거나 실패가 확정되기 전에 ACK하지 않는다. 결과 저장·알림 발행·ACK의 정확한 순서와 복구 절차는 후속 설계에서 정한다.
- 브로커는 작업 분배·미확인 메시지 수 제한·재전달을 담당한다. 워커는 AI 주소와 호출 계약을 알고 있어야 하며, 브로커가 실제 GPU 상태나 분석 비용을 스스로 알아내는 구조는 아니다.
- AI와 워커를 함께 증설하면 소비 용량이 늘어나는 것을 검증한다. 브로커 자체가 AI의 연산 능력을 높인다고 가정하지 않는다.

RabbitMQ의 prefetch와 수동 ACK는 이러한 전달 제한을 구현하는 예시이며 제품 선정은 아니다. prefetch는 실제 AI 실행 수가 아니라 미확인 메시지 수를 제한하므로, 워커의 실행 방식과 ACK 시점을 함께 맞춰야 한다. 근거: [Consumer Acknowledgements and Publisher Confirms](https://www.rabbitmq.com/docs/confirms).

## 완료 기한과 결과 회수

요청 접수부터 큐 대기·AI 분석·결과 저장·사용자 결과 표시까지 포함한 전체 완료 기한 T를 둔다. 구체적인 T는 미정이며 원하는 사용자 대기 시간과 실제 분석 시간 측정으로 결정한다. 완료 가능성이 낮은 요청은 일찍 거절하는 방향으로 검토하되, 수락 기준과 큐 크기는 측정 전 확정하지 않는다. 기한이 지난 미시작 작업은 실행하지 않는다.

T가 지나면 현재 사용자 요청은 실패로 종료한다. 이미 진행 중인 분석은 이후 완료되더라도 결과를 저장해 다음 요청에서 재사용한다. 사용자 응답 기한과 분석 실행·결과 보존의 수명을 구분한다. 실행 중 분석의 취소 정책은 미정이다.

워커 장애 이후에도 기존 AI 분석을 식별하고 결과를 회수하는 것을 필수 검토 요구로 둔다. 안정적인 analysisId로 기존 실행의 상태·결과를 먼저 확인하며, 재전달만으로 무조건 새 분석을 시작하지 않는다. 이를 위해 AI 측 실행 식별·상태 조회·결과 보존 지원이 필요하다. 현행 HTTP 계약이 이를 제공한다고 가정하지 않으며 지원 가능성·보존 기간·실행 ID와 영상 ID의 관계는 후속 확인 대상이다.

워커와 브로커의 연결이 끊겨도 AI 분석이 계속 실행될 수 있다. 따라서 브로커의 전달 제한만으로 장애 상황의 AI 실행 상한이나 중복 실행 방지를 보장하지 않는다. 이전 실행 확인과 중복 호출 방지·결과 저장의 멱등성은 별도 설계·검증한다.

결과는 DB에 보존하고 완료 메시지는 대기 중인 API 요청을 깨우는 알림으로 사용한다. API 서버는 저장된 결과를 최종 기준으로 응답하며 알림을 놓친 경우에도 기한 안에서 저장 상태를 다시 확인한다. 결과 저장과 알림 발행 사이의 실패 복구, 원래 API 인스턴스로의 알림 전달, 재전달·중복 알림 처리는 아직 확정하지 않았다. 완료 알림이 작업 큐와 같은 브로커를 사용할지도 제품 선정과 함께 정한다.

## 현행 결정과의 차이

ADR 0003은 앱 내부 분석과 MySQL 전역 슬롯을 선택하고 별도 분석 작업의 인계·재개를 보장하지 않는다. ADR 0004도 실행자 장애 시 실패를 확정하고 다음 동기화에서 재분석하는 정책이다. 이번 검토안의 별도 워커, 장애 후 기존 실행 결과 회수, 요청 종료 이후의 결과 저장은 그 경계와 다르다. 실제 채택 시에는 기존 소유권·fencing·공유 분석 정책과 늦은 결과 저장을 어떻게 조정할지 결정하고 관련 ADR을 재검토해야 한다. 이번 기록만으로 현행 정책을 바꾸지 않는다.

기존 MySQL 전역 슬롯도 이미 동시 호출을 제한한다. 또한 HTTP 단일 진입점으로 인스턴스 주소를 숨길 수 있으므로, 브로커가 없으면 API 서버가 모든 AI 인스턴스를 알아야 한다는 전제는 사용하지 않는다. 근거: [Application Load Balancer 설명](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/introduction.html).

## 대안과 채택 판단

| 대안 | 비교할 내용 |
|---|---|
| HTTP 단일 진입점 + AI 측 실행 제한 | 인스턴스 은닉과 과부하 보호를 더 단순하게 충족하는가 |
| 별도 워커 + DB 작업 큐 | 기존 MySQL로 분배·대기·기한·복구를 구현하는 비용은 얼마인가 |
| 별도 워커 + 메시지 브로커 | 소비 제한·분배·재전달의 이득이 브로커 운영과 결과 전달 비용보다 큰가 |

검증할 가설은 다음과 같다. 워커와 AI를 한 쌍으로 확장할 때 브로커의 작업 분배·소비 한도·재전달을 사용하는 편이 DB 큐로 같은 기능을 구현하는 것보다 전체 구현·운영 부담이 작으며, HTTP 대안보다 일시적인 요청 집중을 완료 기한 안에서 흡수하기 쉽다. 이 가설이 성립하지 않으면 브로커를 도입하지 않는다.

판단 전에 실제 AI의 분석 시간 분포와 인스턴스별 안전 동시성을 측정한다. 각 대안은 같은 입력·AI 용량·완료 기한으로 비교하고, AI 증설 시 변경할 코드·설정, 처리량, 기한 내 성공률, 대기 시간, 초과 요청 거절 동작, 장애·중복 실행 복구 복잡도, 인프라 운영 비용을 확인한다. 현재 저장소의 [스텁 기반 기준선](../perf/youtube-sync-baseline.md)은 실제 AI 용량이나 브로커의 효과를 입증하는 자료로 사용하지 않는다.

T·C의 값, 브로커 제품, 큐 크기, 수락·재시도·취소 정책, AI 실행 조회 계약, 결과 보존 기간과 알림 발행 보장 방식은 미정이다. 기존의 회원 간 영상 분석 결과 공유·진행 중 분석 합류와의 정합성도 검증한다. 후속 검증과 채택 결정 전에는 구현·전환을 진행하지 않는다.
