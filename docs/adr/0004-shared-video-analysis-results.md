# 영상 분석 결과와 진행 중 분석을 시스템 전체에서 공유한다

영상 분석 결과는 회원에게 귀속되지 않으며, 같은 YouTube 영상 ID를 사용하는 모든 회원과 애플리케이션 인스턴스가 공유한다. SUCCESS·NOT_FOUND는 시간 만료 없이 재사용하고, 아직 분석 중이면 같은 분석의 완료를 함께 기다린다(singleflight). 회원별로 다시 분석하는 대안보다 중복 호출을 줄일 수 있지만, 오래된 결과와 가이드를 찾지 못했다는 판단도 계속 유지되며 자동 갱신·강제 재분석은 이번 성능 루프에서 다루지 않는다. 나들이 가이드의 동일성과 기존 필드 보존은 ADR 0001을 유지하고, 회원별 위시리스트와 삭제 의사는 서로 공유하지 않는다.

이미 FAILED인 분석을 만난 새 동기화는 새 분석을 시작할 수 있다. 함께 기다리던 분석이 FAILED가 되면 현재 참여 동기화들은 해당 영상을 실패로 집계하고, 같은 동기화 안에서 자동 재시도하지 않는다. 실행 인스턴스가 죽으면 기존 동기화 heartbeat 만료 감지로 실패를 확정하고 대기자도 해당 영상의 대기를 끝낸다. 만료된 실행자의 늦은 저장을 거부하며, 실패한 영상은 다음 동기화에서 다시 분석한다. 따라서 실행자 장애가 그 결과를 기다리던 다른 회원에게도 영향을 줄 수 있다.

이 결정은 ADR 0003의 분석 공유 범위를 보완한다. 분석은 앱 내부에서 실행하고 인스턴스 간 조정은 MySQL을 사용하며, 별도의 분석 Job 실행기·lease·heartbeat나 작업 인계·재개를 도입하는 결정은 아니다. 기존 동기화 소유권과 fencing을 공유 분석에 어떻게 연결할지는 구현에서 검증한다. 근거와 측정·판정 기준은 [성능 루프 #313](https://github.com/100-hours-a-week/KTB4-8th-BE/issues/313)에 기록한다.

진행 중 분석이 있으면 완료 이력보다 먼저 합류한다. 진행 중 분석이 없으면 완료 시각이 가장 큰 이력을 선택하고, 시각이 같으면 ID가 큰 이력을 선택한다. 완료 시각이 없는 이전 계약의 이력은 가장 오래된 것으로 본다. 선택한 이력이 완료 시각과 가이드 매핑을 갖춘 SUCCESS 또는 완료 시각이 있는 NOT_FOUND이면 재사용한다. FAILED, 완료 시각이 없는 이력, 가이드 매핑이 없는 SUCCESS는 다시 분석한다. 실행권 획득 후 재사용할 결과를 발견하면 이번 호출이 삽입한 아직 전송하지 않은 IN_PROGRESS 행만 삭제한다. 이는 실행권 예약을 되돌리는 것이며, 완료된 분석 이력을 임의로 삭제하는 예외가 아니다.

실행권을 얻기 전에 배치가 실패한 영상은 해당 동기화의 처리·실패 수에만 반영하고 분석 이력은 만들지 않는다. 시도하지 않은 FAILED 이력이 다른 동기화의 최신 완료 결과를 가리지 않게 하기 위한 선택이다. 실행권을 얻은 영상은 기존 IN_PROGRESS 이력을 FAILED로 마감한다. 재사용·합류한 영상도 이번 동기화 이름의 분석 이력을 추가하지 않는다.

배포는 모든 인스턴스의 동기화 신규 접수와 분석 쓰기를 중단하고 실행 중 작업을 종료한 뒤 진행한다. `video_analysis`의 상태·완료 시각과 스키마를 백업하고 V9를 먼저 적용한다. 정리 UPDATE부터 유일 키 ALTER가 끝날 때까지 구버전 워커를 포함한 모든 쓰기를 막아야 한다. 마이그레이션 완료, `in_progress_video_id` 생성 컬럼과 `uk_video_analysis_in_progress_video` 유일 키를 확인한 뒤 신버전을 배포하고 접수·워커를 재개한다. DDL 실패 시 쓰기 중단을 유지하고 UPDATE가 이미 반영됐는지와 중복 행·스키마를 확인해 [운영 적용 #309](https://github.com/100-hours-a-week/KTB4-8th-BE/issues/309)의 복구 절차를 따른다. 실패한 V9를 무조건 재실행하거나 Flyway 이력만 repair하지 않는다. 기동 시 제약 검사는 후속 판단으로 둔다.

운영 적용 전 `information_schema.columns`에서 `video_analysis.video_id`와 `in_progress_video_id`의 실제 collation을 확인한다. 통합 테스트는 `utf8mb4_0900_bin` 스키마에 V1~V9를 적용하고 두 컬럼 모두 `utf8mb4_0900_bin`인지 검증하며, 이는 운영 DB의 확인을 대신하지 않는다. 원본 컬럼이 대소문자를 구분하지 않는 환경은 #309에서 조회·정리 쿼리의 비교 기준을 맞춘 뒤 적용한다. 완료 시각은 현재 애플리케이션 시각을 유지하며, 인스턴스 간 시계 오차 제거를 위한 DB 시각 통일은 #309에서 후속 검토한다.

운영 호출자가 없는 `DefaultYoutubeVideoAnalyzer` → `VideoAnalysisManager.start(videoIds)` 경로 삭제는 목적이 다른 후속 PR로 분리한다. 이 경로를 공유 분석에 다시 연결하지 않는다. 슬롯을 잡은 채 실행권을 획득하는 DB 왕복과 합류 폴링은 이번 PR에서 유지하며, #313의 슬롯 점유·DB active/pending 측정에서 기준선보다 나빠지면 백오프와 경량 조회를 먼저 검토한다.
