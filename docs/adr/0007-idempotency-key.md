# 클라이언트 요청의 중복 처리는 Idempotency-Key와 MySQL로 한다

타임아웃 뒤 재전송이나 더블클릭이 완료된 요청을 새 요청으로 처리하지 않도록, 상태를 바꾸는 API는 클라이언트가 보낸 `Idempotency-Key` 헤더로 중복을 판정한다. 현재는 회원 ID 기준 진행 중 잠금(추천·채팅 guard)과 자연키 upsert만 있어서, 이미 끝난 요청의 재전송을 새 요청과 구별하지 못한다. 대상은 클라이언트에서 BE로 오는 요청뿐이며, BE에서 AI 서버나 외부 API로 가는 호출의 멱등성 키는 이 결정에 포함하지 않는다.

키와 응답은 MySQL 테이블에 저장한다. 유일 범위는 `(회원, 엔드포인트, 키)`이고, 요청 본문 해시를 함께 저장한다. 같은 키의 요청이 처리 중이면 `409`와 `Retry-After`로 거절하고, 본문 해시가 다르면 `422`로 거절한다. 완료된 요청은 저장된 응답을 재생한다. 5xx와 타임아웃으로 끝난 요청은 키를 해제해 같은 키로 다시 실행할 수 있게 하고, 4xx는 저장해 재생한다. 처리 중 인스턴스가 죽어 남은 키는 만료 시간(60초) 뒤 회수한다. 완료된 키는 24시간 보관하고 스케줄러가 만료분을 삭제한다. 키는 형식을 검증하지 않고 그대로 저장하되, 비어 있거나 255자를 넘으면 `400`으로 거절한다.

SSE 응답은 이벤트를 저장하지 않는다. 같은 키로 진행 중이면 `409`를 반환하고, 완료됐으면 최종 결과만 재생한다. 헤더는 처음에는 선택으로 도입해 없으면 기존 동작을 유지하고, FE 적용을 확인한 뒤 필수로 전환한다. 각 기능의 최신 버전에만 적용하며 v1 중복 엔드포인트는 대상에서 제외한다. 이미 중복이 흡수되는 YouTube 동기화 v2·v3, 추천 v2, 취소·삭제류도 키를 적용하지 않는다.

저장소로 Redis를 쓰는 대안은 택하지 않았다. Redis 의존성은 있지만 기본 구현은 Caffeine이라 다중 인스턴스에서 보장되지 않고, 키 확정과 도메인 쓰기를 한 트랜잭션으로 묶을 수 없다. [ADR 0003](0003-in-process-analysis-mysql-coordination.md)에서 인스턴스 간 조정을 MySQL 조건부 갱신으로 하기로 한 선례와도 맞다. 대신 키 조회·삭제가 DB 부하가 되므로, 부하가 문제가 되면 Redis 도입을 다시 검토한다. 서버가 요청을 끝까지 처리한 뒤 응답 저장 전에 죽으면 재실행될 수 있어, 정확히 한 번 실행은 보장하지 않는다.
