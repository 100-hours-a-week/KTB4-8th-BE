# 분석은 앱 내부에서 실행하고 인스턴스 간 조정은 MySQL로 한다

YouTube 동기화의 영상 분석은 요청을 처리하는 애플리케이션 인스턴스 안에서 실행하고, 분석을 위한 DB Job·실행기·lease·heartbeat는 두지 않는다. 회원당 동기화 하나를 `youtube_sync` 행으로 표현하고, `QUEUED`·`RUNNING`일 때만 채워지는 생성 컬럼의 유일 제약으로 중복 실행을 막는다. 실행 인스턴스는 heartbeat를 갱신하고, 모든 인스턴스의 sweeper가 60초 넘게 끊긴 동기화와 그에 속한 미완료 분석을 FAILED로 정리한다. 배치 커밋은 같은 트랜잭션에서 실행 인스턴스와 `RUNNING` 상태를 조건으로 동기화 행을 갱신해, 만료된 이전 실행자의 쓰기를 거부한다(fencing). AI 호출의 전역 동시 상한은 `ai_call_slot` 행 임대로 지키고, 임대가 만료된 슬롯은 다른 인스턴스가 회수한다. 임베딩은 외부 부수 효과이므로 분석과 같은 트랜잭션에서 아웃박스 행으로 기록하고, 폴러가 최소 한 번 실행한다.

이 결정은 [ADR 0002](0002-durable-ai-jobs.md)를 대체한다. 분석은 동기화 요청 수명 안에서 실행되고, 배치마다 결과가 커밋되어 다음 동기화가 성공한 분석을 재사용한다. 인스턴스가 죽으면 그 동기화만 실패하고 남은 영상은 다음 동기화에서 다시 분석하면 된다. 따라서 분석 전면에 DB Job과 lease·heartbeat·인계를 도입하는 대안은 재개·재시도 상태를 중복 저장하고 복구 경로를 늘리면서 얻는 이득이 적다. 인스턴스 간 조정을 Redis로 옮기는 대안도 검토했으나, 현재 규모에서는 동기화 행·heartbeat·sweeper·fencing·슬롯 임대를 MySQL의 조건부 갱신만으로 구현할 수 있어 필수 인프라를 늘릴 이유가 없다. Redis는 성능 단계에서 다시 검토한다.

다중 인스턴스를 전제로 설계하되 1대에서도 같은 코드 경로로 동작한다. 모든 시각 비교(heartbeat, sweeper, 임대, 다음 시도 시각)는 DB 시간을 쓴다. 인스턴스 간 전역 공정성, 분석 작업의 인계·재개, 임베딩의 정확히 한 번 실행은 보장하지 않는다. Guide 동일성·보존 규칙은 [ADR 0001](0001-guide-identity-and-recurring-events.md)을 유지한다. 상세 설계와 인수 조건은 [#248](https://github.com/100-hours-a-week/KTB4-8th-BE/issues/248)을 따른다.
