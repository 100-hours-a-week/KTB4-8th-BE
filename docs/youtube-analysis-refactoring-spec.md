# YouTube 영상 분석·재사용·복구 및 임베딩 전달 구현 명세

## Problem Statement

회원은 YouTube 좋아요 영상에 담긴 장소와 행사를 위시리스트로 가져오기를 원한다. 현재 영상 분석은 한 영상의 복수 가이드를 충분히 표현하지 못하고, 겹치는 동기화 요청의 중복 분석·동시 저장, 분석 이력 재사용, 호출 실패와 프로세스 종료 이후 복구를 일관되게 처리하기 어렵다. 분석·저장·임베딩·위시리스트 반영의 수명이 섞여 있어 일부 작업의 실패가 다른 성공 결과나 응답 시간에 영향을 줄 수 있다.

목표는 기존 동기화 API와 가이드 반환 계약을 유지하면서 성공한 결과를 보존하고, 재사용 가능한 결과의 불필요한 AI 호출을 줄이며, 중복 요청·재시도·소유권 인계·프로세스 재시작에도 저장 결과와 실행 상태가 일관되게 남는 구조로 전환하는 것이다.

## Solution

영상별 분석 결과와 AI 실행 작업을 분리한다. 이미 분석한 영상은 최신 확정 이력을 재사용하고, 진행 중인 영상은 기존 작업에 합류하며, 신규 영상만 최대 10개씩 분석한다. 각 배치의 가이드·영상별 결과·연결·신규 가이드 임베딩 작업을 원자적으로 저장한다.

분석과 임베딩은 DB에 영속화한 공통 AI Job으로 실행·재시도·복구한다. 호출자는 유한한 대기 후 저장된 성공 결과를 받을 수 있고, 남은 분석과 임베딩은 호출자 연결과 무관하게 진행한다. 임베딩 실패는 분석 결과를 되돌리지 않는다. 늦게 완료된 결과는 다음 동기화에서 위시리스트에 반영한다.

기존 데이터와 모든 가이드 쓰기 경로를 새 동일성 규칙에 맞춰 이관한다. 외부 AI 계약·운영 DB·참조 데이터·벡터 정리·복원 절차가 검증되어야 실제 배포를 허용한다.

3. As a 회원, I want 전체 입력이 10개를 넘어도 처리되기를 원한다, so that 좋아요 목록을 인위적으로 잘라 동기화하지 않아도 된다.
4. As a 회원, I want 다른 요청과 겹치는 영상의 진행 중 분석에 합류하고 싶다, so that 같은 영상을 중복 분석하지 않는다.

## Implementation Decisions

### 1. 경계와 책임

- YoutubeVideoAnalyzer의 기존 analyze와 List<OutingGuide> 반환형을 유지한다. 상위 코드가 생성한 AnalysisRequestContext를 받는 내부 오버로드를 추가한다.
- DefaultYoutubeVideoAnalyzer는 입력 검사·중복 제거·작업 확보·실행 요청·대기·결과 통합을 담당한다. 기존 영상 적격성 필터의 동작은 유지하고 전체 입력 개수에는 10개 제한을 적용하지 않는다.
- VideoAnalysisWorkService는 최신 이력 재사용·활성 작업 공유·신규 등록과 배치 구성을 담당한다. VideoAnalysisResultService는 응답의 원자 저장과 미완료 분석 종료를 담당한다. 기존 VideoAnalysisManager의 책임을 이 경계로 분리한다.
- 공통 실행 계층은 AiRequestJobService·Executor·Handler·RetryPolicy로 구성하고 분석 전용 DTO에 의존하지 않는다. 분석 Handler는 응답 해석·후보 검증·저장 재시도를, 임베딩 Handler는 전달과 완료 처리를 담당한다.
- 단순 변환·검증·통합만을 위한 불필요한 별도 클래스는 만들지 않는다. 기존 클래스도 수정·대체 대상으로 취급한다.

### 2. 작업·이력·상태 모델

- AiRequestJob은 분석과 임베딩의 논리적 실행 단위다. 소유자·실행 버전·heartbeat·lease·등록 시각·기한·누적 호출 수·다음 재시도 시각·최종 실패를 보관하며 재시도·인계 시 같은 Job을 유지한다.
- Job 상태는 PENDING·IN_PROGRESS·COMPLETED·FAILED, 영상별 상태는 IN_PROGRESS·SUCCESS·NOT_FOUND·FAILED다. 정상 응답의 영상별 실패를 모두 저장했다면 Job은 COMPLETED일 수 있다.
- 분석 Job 하나는 1~10개 VideoAnalysis로 구성된 VideoAnalysisBatch와 연결된다. VideoAnalysisResult는 분석과 모든 추출 Guide를 연결하고 분석 ID·Guide ID 복합키로 중복 매핑을 차단한다.
- ActiveVideoAnalysis는 영상 ID당 활성 분석 하나를 보장한다. 영상 ID PK의 영구 VideoAnalysisRegistrationLock을 별도로 둔다.
- GuideEmbeddingTask는 임베딩 Job과 대상 Guide를 연결한다. 초기에는 신규 Guide 한 개당 임베딩 Job 한 개이며 실행 상태를 대상에 중복 보관하지 않는다.
- 완료한 분석과 결과 매핑은 불변이다. 후속 요청의 실패 재분석은 기존 실패 이력을 보존한 새 분석·새 Job으로 생성한다.

### 3. 등록·재사용·공유

- 활성 작업을 우선 공유한다. 활성 작업이 없으면 생성 시각·ID 순 최신 완료 이력만 판단한다. 최신 SUCCESS의 모든 결과, NOT_FOUND의 빈 결과는 재사용하고 더 오래된 SUCCESS로 대체하지 않는다.
- 잠금의 영상 ID도 정확한 비교를 적용하며, 영상 ID 순서로 등록 잠금 행을 생성·잠근 뒤 짧은 독립 READ_COMMITTED 트랜잭션에서 활성·최신 완료 이력을 다시 확인한다. 잠금 아래 재조회가 신규 분석 판단 기준이다. 잠금 행은 초기 범위에서 삭제하지 않는다.
- 잠금 아래 최초 판단에서 최신 FAILED 또는 이력 없음이면 신규 후보가 된다. 이미 확보한 공유·재사용 분석 참조는 고정하며, 해당 작업이 실패해도 같은 호출에서 대체 분석을 만들지 않는다.
- 최대 10개 영상 단위로 경쟁 재검증·Job·배치·분석·활성 등록을 함께 커밋한다. 공유·재사용으로 확정된 영상을 제외하고 신규 영상만 배치에 넣는다. 요청 전체를 하나의 긴 등록 트랜잭션으로 묶지 않는다.
- 유일성 예외로 실패한 JPA 트랜잭션을 계속 사용하지 않는다. 잠금 행 생성은 no-op insert 등으로 경쟁을 처리한다. 활성 해제는 영상 ID·분석 ID와 유효 실행권을 조건으로 수행한다.
- 커밋 후 실행을 요청하며 컨텍스트에 확보한 참조를 누적한다. 나중 배치의 등록이 실패하면 예외를 전달하고 남은 등록을 중단하되 앞서 커밋한 Job은 유지한다.

### 4. 실행·소유권·복구

- 유형별 슬롯이 있을 때만 실행권을 원자 획득하고 실행 버전을 증가시킨다. 유효 실행권은 상태·소유자·버전 일치와 DB 현재 시각보다 늦은 lease를 모두 요구한다. 만료된 작업자는 heartbeat로 실행권을 되살리지 못한다.
- 호출 시작 시 실행권·기한·호출 예산 검증과 누적 호출 수 증가를 원자 처리한다. 전송 여부가 불확실한 호출도 예산에 포함한다.
- 분석·임베딩 Job의 기한은 최초 DB 등록부터 각각 10분이다. 대기·재시도·인계를 포함하며 연장하지 않는다. 모든 시간 판정은 DB 시간을 기준으로 한다.
- 재시도 예약은 IN_PROGRESS에서 PENDING 전환·다음 실행 시각 기록·이전 토큰 무효화를 원자 처리하고 기존 heartbeat와 슬롯을 종료·반환한다.
- 소유권 만료 후 기한·예산이 남으면 PENDING으로 복구한다. 총 4회를 소비했고 재사용할 저장 응답이 없으면 CALL_BUDGET_EXHAUSTED로 종료한다. 응답 자체의 별도 영속화는 하지 않는다.
- 기한 초과는 Job 잠금 아래 실행권을 무효화하고 미완료 분석 실패·활성 해제·Job 실패를 함께 저장한다. 확정한 분석·매핑은 변경하지 않는다.
- 기동 직후와 1초 주기로 PENDING 실행·만료 복구·기한 초과 종료를 수행한다. 새 요청 없이도 복구하며 요청은 즉시 wake-up을 제공한다.
- AI worker·heartbeat·dispatch/recovery 실행기를 분리한다. 유형별 독립 슬롯과 페이지 조회를 사용하고 실행 가능 작업을 다음 실행 시각·등록 시각·ID 순으로 선택한다. 전체 대기 작업을 실행기 메모리에 적재하지 않는다.
- 여러 인스턴스가 같은 실행권 규칙을 따르되 병렬도는 인스턴스 단위다. 인계 전에 전송한 외부 호출은 겹칠 수 있으며 실제 외부 in-flight의 엄격한 상한과 정확히 한 번 실행은 보장하지 않는다.

### 5. HTTP·재시도와 초기 설정

- Job 전용 HTTP 클라이언트를 사용하여 채팅·추천의 공유 클라이언트 정책을 바꾸지 않는다. HTTP 전체 제한은 연결과 응답 수신을 포함하고 남은 Job 기한을 넘지 않는다.
- 성공은 성공 DTO, 비정상 HTTP·전송 오류·타임아웃은 AiRequestException으로 전달한다. 상태 코드·Retry-After·원인을 보존하고 오류 본문 파싱 실패와 무관하게 HTTP 상태로 분류한다.
- AI 재시도는 공통 실행 계층 한 곳에서 최초 1회와 최대 3회 수행한다. 기본 대기는 1·2·4초에 ±20% jitter이며 HTTP 클라이언트의 숨은 재시도는 제거한다.
- 연결 실패·연결/응답 타임아웃·HTTP 408·429·500·502·503·504는 재시도하고 나머지 HTTP 오류와 응답 계약 위반은 최종 실패한다. 정상 응답의 영상별 실패·후보 검증 실패도 즉시 재호출하지 않는다.
- Retry-After의 초 단위·HTTP 날짜를 모두 지원하고 유효하면 기본 backoff보다 우선한다. 과거 시각은 대기 0, 잘못된 값은 기본 backoff로 처리한다. 다음 실행 시각이 deadline 이상이면 기한 내 재시도 불가로 종료한다.

| 설정 | 초기값 |
|---|---|
| 분석·임베딩 병렬도 | 인스턴스당 4·2 |
| 분석·임베딩 HTTP 전체 제한 | 130초·30초, 남은 Job 기한 이내 |
| HTTP 연결 제한 | 5초, HTTP 전체 제한 이내 |
| 분석·임베딩 Job 기한 | 등록부터 각각 10분 |
| heartbeat·lease | 10초·60초 |
| 실행·복구 스캔 | 기동 직후 및 1초 주기 |
| 호출자 대기 예산·polling | analyze 진입부터 60초·500ms |
| DB 결과 조회 | 최초 1회 + 재시도 2회, 100·200ms |
| 교착상태 저장 | 최초 1회 + 재시도 2회, 50·100ms에 ±20% jitter |
| 짧은 DB 트랜잭션·결과 저장 | 3초·10초 |
| DB 잠금 대기 | 2초 |

- 모두 설정 가능하게 하고 초기 튜닝 기준으로 취급한다. 실제 HTTP/LB 제한·AI 지연·용량에 맞춰 배포값을 검증한다.
- DB connection 획득·statement·잠금 대기·transaction 제한이 위 예산 안에서 동작해야 한다. 프레임워크 어노테이션만으로 모든 제한을 보장한다고 가정하지 않는다.

### 6. 응답 구조·후보 검증·동일성

- 분석 AI는 영상 ID·상태·실패 정보와 영상별 Guide 목록을 반환하며 Guide 유형 PLACE/EVENT를 명시한다. category로 유형을 추론하지 않는다. 실제 URL·wire 필드명은 버전 계약서와 계약 테스트로 고정하며 구계약으로 조용히 fallback하지 않는다.
- SUCCESS는 Guide 1개 이상, NOT_FOUND·FAILED는 빈 목록만 허용한다. 요청 ID와 응답 ID는 정확히 대응해야 한다.
- 파싱 실패·ID 누락/중복/미요청 ID·알 수 없는 상태/유형·필수 구조 위반은 INVALID_AI_RESPONSE로 배치 전체 최종 실패한다. 정상 영상별 FAILED는 다른 결과와 함께 저장한다.
- 구조 유효성과 저장 가능성을 구분한다. 계약상 허용한 후보 필드 누락은 후보 검증으로 처리한다.
- 이름·도로명주소 null/공백 또는 각각 VARCHAR(255) 길이 초과, 좌표 누락/비유한 값/위도 [-90, 90]·경도 [-180, 180] 범위 위반, 양쪽 행사 날짜가 있고 시작일이 종료일보다 늦은 후보, 기타 DB 저장 제약 위반 후보는 제외한다. 제외 위치·사유를 분석 이력에 남긴다.
- 유효 후보는 유지하고 전부 제외되면 해당 영상만 FAILED / INVALID_GUIDE_DATA로 기록한다. 영업시간·행사 날짜 미상은 허용하고 임의 값을 만들지 않는다. 날짜 한쪽만 주어지면 해당 값만 보존한다.
- GuideKey·isSameAs·DB 유일성은 유형·최초 입력 이름·도로명주소의 정확한 원문 비교를 사용한다. trim·대소문자 변환·유니코드 정규화·길이 절단을 하지 않는다. 충돌 시 기존 ID와 모든 기존 필드를 보존한다.
- 장소와 행사는 별개 유형이며 행사 회차·기간은 동일성에 포함하지 않는다. 같은 이름·주소의 반복 행사는 이전 기간을 유지하여 새 회차의 이용 가능성에서 제외될 수 있다는 제약을 수용한다.
- 새 행사의 날짜는 Asia/Seoul 기준 시작일 자정 포함, 종료일 다음 날 자정 미포함으로 저장하고 이용 가능성 비교도 해당 경계와 일치시킨다. 충돌한 기존 가이드의 기간을 이 이유로 갱신하지 않는다.

### 7. 트랜잭션·저장·최종 실패

- YouTube 조회와 분석 대기는 트랜잭션 밖에서 수행하고 위시리스트 반영만 짧은 별도 트랜잭션으로 처리한다. V2·V3 모두 등록·결과 저장이 상위 트랜잭션과 독립적으로 커밋되어야 한다.
- AI 호출은 DB 트랜잭션 밖에서 수행한다. 결과 저장은 Job 잠금 아래 실행권·lease·기한을 검증한 뒤 Guide·모든 매핑·영상별 상태·활성 해제·신규 임베딩 Job/대상·분석 Job 완료를 배치별 한 트랜잭션으로 처리한다.
- 저장·인계·기한 초과 종료는 같은 Job 잠금으로 직렬화한다. 기한 내 저장 검증에 성공한 트랜잭션은 유한한 DB 제한 안에서 기한 이후 커밋할 수 있다. 저장 잠금 때문에 heartbeat가 대기해도 이 사실만으로 유효한 저장을 취소하지 않는다.
- Guide는 모든 배치에서 유형·이름·주소의 고정 순서로 원자 생성/충돌 처리한다. 기존 필드를 덮어쓰지 않고 기존 ID를 확보한다. 전체 요청의 반환 중복 제거를 저장 선행 조건으로 두지 않는다.
- 교착상태는 같은 AI 응답으로 새 저장 트랜잭션 전체를 제한 재시도하고 매번 실행권·lease·기한을 재검증한다. 재시도 소진과 다른 저장 실패는 전체 롤백 후 별도 트랜잭션에서 최종 종료한다.
- 최종 실패는 Job 서비스의 트랜잭션에서 Handler.onFinalFailure와 업무 종료를 함께 수행한다. 이 경로는 외부 호출·독립 커밋을 하지 않으며 순환 의존성을 방지한다.
- 별도 실패 기록 시 실행권을 잃으면 이전 작업자는 상태를 바꾸지 않고 새 소유자나 복구에 맡긴다. 실패 기록 자체가 불가능하면 로그를 남기고 후속 복구가 동일한 원자적 종료를 수행한다.

### 8. 호출자 대기·반환·위시리스트

- 컨텍스트는 호출 ID·영상별 고정 분석/배치/Job ID·생성/공유/재사용 구분을 보관한다. 해당 ID로 조회하고 이후의 최신 이력으로 대체하지 않는다.
- analyze 진입부터 단조 시계로 60초 예산을 계산한다. 입력 준비·등록이 소비한 시간을 차감하되 예산 만료만으로 미등록 입력을 버리지 않는다. 전체 입력 상한이 없으므로 메서드 전체나 HTTP 요청 전체의 60초 반환은 보장하지 않는다.
- 정상 최종 조회는 분석 상태·결과 매핑을 같은 일관된 스냅샷으로 읽는다. 재사용 결과와 저장된 성공 결과를 GuideKey로 중복 제거하며 반환 순서는 보장하지 않는다. 결과가 없으면 빈 목록을 반환한다.
- 대기 상태는 COMPLETED·WAIT_TIMEOUT·INTERRUPTED다. COMPLETED는 고정 분석들이 모두 종료되었다는 의미이며 모두 성공했다는 의미는 아니다. 영상별 결과는 이력으로 구분한다.
- 대기 제한 시 저장된 성공 부분을 반환하고 작업은 계속 실행한다. 최종 조회 이후 커밋한 결과는 이번 반환에 포함하지 않는다.
- 인터럽트 시 새 blocking 조회를 강제하지 않고 재사용 결과를 포함한 마지막 성공 조회 결과를 반환한다. INTERRUPTED와 호출자 interrupt flag를 보존하며 worker를 취소하지 않는다.
- DB 조회의 제한 재시도가 소진되면 캐시된 부분 결과나 빈 목록으로 대체하지 않고 예외를 전달한다. 이미 커밋한 결과·Job은 보존한다.
- 백그라운드 Job은 위시리스트를 수정하지 않는다. 늦게 완료된 결과는 다음 동기화에서 반영하며 다음 동기화가 없으면 자동 반영되지 않는다. 위시리스트 반영 실패도 커밋한 분석을 되돌리지 않는다.
- V2·V3 plain 동기화의 기존 외부 경로·HTTP 응답 형식을 유지한다. 성공 응답이 모든 영상의 분석·반영 완료를 뜻하지 않는다는 계약을 명시한다. 부분 완료 구분은 내부 상위 서비스·관측에서 제공한다.

### 9. 임베딩 전달

- 신규 Guide만 분석 저장과 같은 트랜잭션에서 임베딩 Job/대상으로 등록한다. DB Job 테이블을 Transactional Outbox로 사용한다.
- 장소·행사 모두 Guide ID로 외부 upsert하며 중복 요청이 중복 벡터를 만들지 않아야 한다. 성공 응답은 실제 저장 완료를 의미해야 하며 단순 접수 응답만으로 Job을 완료하지 않는다.
- 지원하지 않는 서버에 대한 별도 상태 조회 프로토콜은 추가하지 않고 배포를 보류한다. 외부 정확히 한 번 실행은 보장하지 않는다.
- 임베딩 완료는 analyze가 기다리지 않는다. 임베딩 최종 실패는 분석 결과·반환을 변경하지 않고 실패 상태를 보존한다.

### 10. 스키마·기존 데이터·전환

- Flyway baseline과 버전 SQL을 명시적으로 준비하고 기존 DB를 자동 baseline하지 않는다. 운영 Hibernate는 validate로 사용하며 실제 MySQL 통합 테스트도 Flyway로 스키마를 생성한다.
- Job·배치·활성 등록·등록 잠금·임베딩 대상과 FK·연결 유일성을 추가하고, 분석 완료·실패·제외 정보와 결과 복합키를 보장한다. 배치가 없는 과거 이력은 보존하고 신규 작업에만 배치 연결을 필수로 한다.
- 최신 이력용 영상 ID·생성 시각·ID 복합 인덱스와 실행 가능 시각·기한 조회 인덱스를 실제 실행 계획으로 검증한다.
- 데이터 정리 후 유형·이름·도로명주소 NOT NULL과 복합 유일성을 적용한다. 이름·주소는 각각 VARCHAR(255), 문자 집합·연결은 utf8mb4, collation은 utf8mb4_0900_bin이다. MySQL 8.0.17 이상과 실제 지원 여부를 확인하며 다른 비교로 대체하지 않는다.
- 정확한 키별 최소 ID를 대표 가이드로 고정하고 기존 ID→대표 ID 매핑을 영속화한다. 대표 필드를 병합하거나 덮어쓰지 않는다.
- 분석 매핑은 대표 ID로 중복 제거하여 재생성하고 코스는 순서·개수를 유지한 채 Guide FK만 치환한다. 같은 회원·대표 Guide의 활성 위시리스트는 최소 ID 하나를 유지하고 나머지를 삭제 처리하며 기존 삭제 이력과 행 식별자를 보존한다.
- 외부 벡터의 중복 ID 정리와 대표 ID 존재·검색 가능성 검증을 일회성 이관에 포함한다. 구 ID가 검색 결과에 남지 않아야 한다.
- null/공백 키·길이 초과 등 기존 오류는 자동 삭제·임의 보정·절단하지 않는다. 대상 ID와 참조 수를 보고하고 검증된 정정 목록을 준비하며 미해결이면 제약 적용을 중지한다.
- 구버전 작업자를 정지한 뒤 기존 IN_PROGRESS를 FAILED / LEGACY_MIGRATION으로 종료한다. 새 Job으로 복원하지 않고 완료 이력을 유지한다.
- V2의 직접 저장·동기 임베딩 경로를 포함한 전체 생성 경로·동일성 비교 사용처를 전환한다. V2·V3는 같은 analyzer와 고정 ID 컨텍스트를 사용한다.
- 관련 동기화·Guide 쓰기를 짧게 중단하고 구버전 작업자를 정지한 뒤 정리·이관·제약 검증을 수행한다. 호환 버전만 실행하고 검증 후 쓰기를 재개한다.
- 이관 전 백업과 DB·벡터 복원 리허설을 완료한다. 정리 이후 구버전 바이너리만 다시 배포하는 롤백은 허용하지 않는다. 호환 버전으로 수정하거나 쓰기를 중단하고 검증한 복원 절차를 적용한다.

### 11. 외부 검증·배포 조건

아래 조건은 이미 확인된 지원 사실이 아니다. 구현 중 검증 자료를 준비하고 실제 배포 전에 모두 통과해야 한다. 실패하면 가정·우회·구계약 fallback으로 진행하지 않고 배포를 보류한다.

| 대상 | 통과 조건과 증거 |
|---|---|
| 분석 AI | 버전 계약서에 실제 URL·wire 필드명을 고정하고 복수 응답·명시적 유형·ID 대응·오류 구조 계약 테스트 통과 |
| 임베딩 AI | 같은 Guide ID 중복 호출 후 벡터 중복 없음, 성공 응답 이후 실제 저장·검색 가능 확인. 접수만 지원하면 미통과 |
| 운영 MySQL | 실제 버전·컬럼·collation SQL preflight 및 Java/DB 동일성·길이·유일성·잠금 테스트 통과 |
| 기존 데이터 | 잘못된 데이터·중복·참조 보고서, 검증된 정정 목록, 참조·위시리스트·코스·외부 벡터 이관 리허설, 미해결 오류 0건 |
| HTTP·AI 용량 | 프록시/LB 제한과 실제 지연·용량 측정으로 대기·호출·병렬 설정 검증 및 배포값 조정 |
| 운영 전환 | 전체 쓰기 경로 목록과 차단 확인, 구버전 정지, 호환 버전 전환, 백업 및 DB/벡터 복원 리허설 통과 |
| CI | Flyway 기반 실제 MySQL 통합 검사를 필수 작업으로 실행하여 통과. bootJar만으로 대체하지 않음 |

### 12. 관측

- 호출 ID·Job ID·배치 ID·분석 ID·실행 버전·실패 코드를 로그에 남겨 생성·공유·재사용·인계·종료를 추적한다.
- 활성 수, 유형별 PENDING·대기 시간·실행 수, 기한 초과·인계·AI 호출·재시도, 저장 교착상태·재시도, heartbeat 실패·대기 중단·조회 장애·임베딩 최종 실패를 관측한다.

## Testing Decisions

### 확정한 테스트 경계

분석기 진입점·Job 실행·V2/V3 HTTP·이관의 네 테스트 경계를 사용자 확인으로 확정했다. 기존 공개 경계를 우선 사용하고 테스트만을 위한 업무 인터페이스를 추가하지 않는다.

| 경계 | 구동과 관찰 |
|---|---|
| 주 경계: YoutubeVideoAnalyzer | analyze와 상위 생성 컨텍스트로 입력한다. 실제 서비스·Repository·Flyway MySQL을 연결하고 제어 가능한 AI HTTP 서버를 사용한다. 반환 Guide·고정 분석 ID·대기 상태·DB 이력/매핑·임베딩 등록·관찰 가능한 외부 요청을 확인한다. 내부 메서드 순서나 Repository 호출 횟수를 인수 조건으로 삼지 않는다. |
| 요청 없는 실행·복구: 공통 Job 실행 경계 | 공개 실행·기동/스캔 경계로 저장된 Job을 처리한다. 별도 애플리케이션 인스턴스/실행 소유자의 경쟁·재시작·시간 경계를 구동하고 DB 최종 상태와 실제 외부 요청 예산을 확인한다. 분석기 호출 없이 복구하는 계약도 이 경계에서 검증한다. |
| 기존 V2·V3 plain HTTP 경계 | 컨트롤러·상위 서비스의 기존 응답, 동일 analyzer 사용, 대기 동안 트랜잭션 해제, 위시리스트 커밋 분리를 확인한다. 핵심 분석 시나리오 전체를 HTTP에서 중복 반복하지 않는다. |
| Flyway·운영 이관 경계 | 실제 MySQL에 대표·중복·null/공백·삭제 이력·코스 참조 fixture를 준비해 baseline·정리·제약·검증·복원 절차를 실행한다. DB와 외부 벡터의 관찰 가능한 정합성으로 판정한다. |

### 테스트 원칙·선행 사례

- 좋은 테스트는 입력·경쟁·오류를 만들고 반환값·저장 결과·외부 계약으로 판정한다. 클래스 분해 방식·private 메서드·호출 순서를 그대로 복제하지 않는다.
- 기존 DefaultYoutubeVideoAnalyzerTest에는 배치 분할·가이드 중복 제거·기존 가이드 재사용·실패·입력 필터 시나리오가 있다. 업무 시나리오를 재사용하되 단일 Guide 응답·동기 임베딩·응답 누락 무시 등 새 계약과 다른 기대는 갱신한다.
- 기존 VideoAnalysisManagerTest에는 Spring 트랜잭션 경계·매핑·종료 상태 불변 테스트가 있다. mock 기반 트랜잭션 기록은 실제 DB 롤백·dirty checking·잠금을 증명하지 않으므로 실제 MySQL 결과 검증으로 보강한다.
- 기존 RecommendationServiceV2Test와 ChatRequestConcurrencyTest의 MockMvc 및 동시 요청 구성은 HTTP 경계 테스트의 선행 사례다. 현재 통과 여부를 이 명세 작성에서 확인했다는 의미는 아니다.
- 순수 동일성·후보 검증·응답 해석·오류 분류·backoff·상태 전이는 빠른 단위 테스트로 보조한다. 시간·jitter는 제어 가능하게 하고 동시성 테스트는 latch/barrier 등으로 경쟁 지점을 재현한다. DB 기한·lease의 최종 판정은 실제 DB 시간으로 검증한다.
- 외부 AI 테스트 대역의 계약 적합성은 별도 서버 계약 테스트로 확인한다. 로컬 대역 통과만으로 실제 서버 지원을 확인했다고 판단하지 않는다.

### 필수 시나리오

1. 전체 10개 초과·중복 입력·기존 적격성 필터·빈 입력, 신규 영상만 배치 구성.
2. 복수 Guide·유형 분리·동일 키 재사용·기존 필드 보존, Java/MySQL의 대소문자·후행 공백·유니코드 및 255자 경계 일치.
3. 정상 미추출·부분 후보 제외·전체 무효·좌표/기간 오류·미상 날짜, 서울 날짜와 종료일 포함 경계.
4. 최신 SUCCESS/NOT_FOUND/FAILED·이력 없음, 오래된 성공 대체 금지·새 실패 이력 보존·고정 참조 대체 금지.
5. 겹치는 요청·등록 충돌 직후 완료·잠금 순서, 같은 Guide의 동시 저장 및 모든 영상 매핑 보존.
6. 등록 일부 커밋 후 실패, 커밋 후 제출 전 종료, 새 요청 없는 기동/주기적 복구.
7. 슬롯 부족·대기 중 기한 초과, 소유권 인계의 누적 예산·기한, 만료 lease 부활·늦은 결과/실패/heartbeat 차단.
8. 총 4회 이후 복구, HTTP 재시도 분류·Retry-After 형식/기한·오류 본문 파싱 실패·숨은 재시도 없음.
9. 잘못된 정상 응답 구조의 배치 실패와 후보별 검증 분리, 정상 영상별 FAILED 혼재의 Job 완료.
10. 배치 원자 롤백·별도 실패 기록·실패 기록 시 실행권 상실·DB 장애 후 복구, 다른 배치 성공 유지.
11. 교착상태는 AI 재호출 없이 전체 저장만 재시도, 저장 잠금 중 heartbeat 대기, 기한 내 검증 후 늦은 커밋과 종료 경쟁.
12. 진입부터 60초 예산·등록 시간 차감·입력 누락 없음, 반환 스냅샷, 대기 중단 부분 결과·인터럽트 플래그·조회 재시도 소진 예외.
13. 연결 종료/대기 취소와 worker 생존 분리, 위시리스트 실패와 분석 커밋 분리, 늦은 결과의 다음 동기화 반영.
14. 신규 Guide만 임베딩 등록·Guide ID 중복 upsert·실제 저장 완료, 분석 응답의 임베딩 비대기·최종 실패 독립성.
15. V2·V3 기존 외부 응답과 새 분석 경로 통합, Job 전용 HTTP 설정의 채팅·추천 영향 없음, 실제 HTTP·DB 제한 동작.
16. 최소 ID 대표·매핑/활성 위시리스트 중복 정리·삭제 이력·코스 순서·벡터 검색 정합성·미해결 데이터 배포 차단.
17. 구버전 쓰기 차단·LEGACY_MIGRATION·Flyway baseline·운영 validate·DB/벡터 복원과 CI 필수 MySQL 검사.

## Out of Scope

- 메시지 브로커, 엄격한 전역 AI 호출 상한, 외부 호출의 정확히 한 번 실행 보장.
- 호출별 Attempt 영속화, AI 응답 자체의 별도 영속화, 등록 잠금 행 정리.
- 여러 Guide의 임베딩 호출 묶음 최적화, 일반 요청에서 기존 Guide 재임베딩, 임베딩 운영 재처리 도구.
- 행사와 회차 분리, 기존 행사 기간 자동 갱신, 원문 키 정규화 또는 가이드 필드 병합.
- 외부 실행 상태 조회 API·새 동기화 응답 DTO·SSE 구현, 백그라운드 Job의 회원 위시리스트 자동 반영.
- YouTube 좋아요 목록 조회 전략·할당량 최적화, OAuth·연동 API 및 별도 legacy 회원 동기화 흐름의 전면 재설계.
- 무중단 데이터 전환 보장, 정리 이후 비호환 구버전 바이너리만 재배포하는 롤백.
- 이번 명세 작성 단계에서의 애플리케이션 구현·운영 데이터 변경·실제 배포.
