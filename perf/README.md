# YouTube 공유 분석 측정 도구

#313의 부모 SHA `0137347`와 병합 SHA `9fea9ba`를 비교한다. 기존 `k6/common.js`의 DB 시각 근사 지표와 새 수신 지표를 섞지 않는다. 이 문서는 실행 방법이며 성능 결과나 채택 판정이 아니다.

## 구성

- Docker compose: MySQL 8.4.8(호스트 13316 포트), k6 2.3.0.
- 호스트 Java 25: 비교 버전별 앱 1개와 AI HTTP 스텁 1개. 앱·MySQL은 반복 중 유지한다.
- 호스트 Python(표준 라이브러리): k6가 호출하는 수신기가 실제 앱의 SSE를 스트리밍으로 읽는다. 완전한 이벤트 프레임의 빈 줄을 받은 `perf_counter_ns` 차이를 주 지표로 삼는다. k6 HTTP 요청 시간은 수신기 호출 전체 시간이므로 주 지표로 쓰지 않는다.
- base: API 18181, 관리 18182, 측정 제어 18183, AI 18180.
- candidate: API 18281, 관리 18282, 측정 제어 18283, AI 18280.
- 수신기: 18300. k6 컨테이너가 접근하도록 모든 인터페이스에 바인딩하므로 로컬 측정 장비에서만 실행한다. 앱 토큰은 수신기가 로컬 파일에서 읽고 원시 기록에 넣지 않는다.

앱 두 개는 같은 MySQL 서버의 별도 스키마를 쓴다. 한쪽만 부하를 실행하고 다른 쪽의 후속 작업도 비어 있는 상태로 둔다. 다른 컨테이너·프로그램의 부하는 별도로 통제해야 한다.

## 기동 (Windows PowerShell)

1. 부모 SHA의 별도 체크아웃을 만든다. 작업 디렉터리를 재사용할 경우 미커밋 변경이 없는지 확인한다.
2. 아래 기동 스크립트가 부모 체크아웃에 동일한 하네스·스텁·빌드 도구만 복사한다. `src/main`은 바꾸지 않는다. 부모 체크아웃에는 측정용 미커밋 변경이 남는다.

```powershell
./perf/start313.ps1 -BaseRoot '<0137347 체크아웃 절대 경로>' -JavaHome '<Java 25 경로>'
```

`BASE_AND_CANDIDATE_READY`까지 기다린다. 시작 시 전용 DB `keepgo_perf_313_base`, `keepgo_perf_313_candidate`를 재생성하고 40명의 회원을 만든다. 기존 기본 성능 DB와 운영 DB는 사용하지 않는다. 실행 로그·측정용 키·토큰·프로세스 목록은 Git에서 제외된 `build/perf/313/`에 둔다. Windows 명령줄 길이 제한을 피하려고 Java 인수 파일을 사용한다. 측정용 토큰만 48시간 동안 유효하다.

## 소규모 검증

```powershell
python -m unittest discover -s perf -p 'test_loop313.py' -v
python perf/loop313.py --base-sha 0137347 --candidate-sha 9fea9ba --warmups 0 --repeats 1 --concurrency 1 --output build/perf/313/smoke-n1
python perf/loop313.py --base-sha 0137347 --candidate-sha 9fea9ba --warmups 0 --repeats 1 --concurrency 5 --scenarios shared --output build/perf/313/smoke-shared-n5
```

원시 기록 덮어쓰기를 막으므로 재실행은 새로운 출력 디렉터리를 사용한다. 스크립트가 실패하면 실패 회차·로그부터 확인한다. 실패 결과를 정상 표본에 섞거나 횟수를 채웠다고 간주하지 않는다. 워밍업 없는 단일 회차의 p50/p95는 도구 검증용이며 개선률 판정에 사용할 수 없다.

## 전체 반복 실행

사용자가 전체 측정을 진행하기로 결정한 후 실행한다. 가이드별 임베딩이 직렬이어서 오래 걸릴 수 있다. 이번 작업의 소규모 실행은 전체 측정을 대체하지 않는다.

```powershell
python perf/loop313.py --base-sha 0137347 --candidate-sha 9fea9ba --output build/perf/313/full
```

기본값은 첫 동기화·30+10 재동기화·동일 영상 30개 공유, N=1·5·10·20, 버전별 워밍업 2회·본 측정 20회다. 회차마다 base→candidate와 candidate→base 순서도 교대로 바꾼다. 회원 40명, YouTube 페이지 50개/200ms, AI 분석 배치 10개/1000ms, 임베딩 호출/1000ms를 유지한다.

## 초기화·검증·통계 경계

- 초기화 전 실행 중 동기화·슬롯·임베딩 아웃박스·AI HTTP 요청이 모두 0인지 확인한다. 아웃박스가 FAILED로 남아도 비어 있다고 처리하지 않는다.
- `/reset`은 POST만 받고 전용 두 스키마만 허용한다. 완료된 후속 작업이 없는 상태에서 FK 검사를 같은 연결에서 잠시 끄고 작업 테이블을 비운다. 실패해도 FK 검사는 복원한다. 회원·Flyway·슬롯 구성·Hibernate ID 시퀀스와 프로세스 내 할당 범위는 유지한다. 매회 논리적 작업 데이터는 같지만 ID 값과 시퀀스 값까지 바이트 단위로 복원하는 방식은 아니다.
- 재동기화는 매회 30개를 먼저 실행하고 후속 작업 완료·최근 결과 창(1초) 경과를 DB에서 확인한다. 이후 목록을 40개로 바꾸고 AI 통계와 DB 샘플링을 새로 시작한다. 고정 대기만으로 완료를 추정하지 않는다.
- 본 실행의 SSE는 accepted·success 수신과 DB의 SUCCEEDED·대상 수·처리 수·실패 수를 함께 검증한다. 실패·누락·예상 밖 SSE 이벤트가 있으면 해당 실행은 중단한다.
- DB active/pending은 본 실행 동안 250ms 간격으로 읽는 관측 최댓값이다. 짧은 피크를 놓칠 수 있다. 모든 요청 이후의 아웃박스 처리는 완료까지 기다려 AI 호출 수에는 포함하되 SSE 지연·DB 표본에는 포함하지 않는다.
- 중복 영상 제출 수는 회차별 AI 요청 영상 ID 출현 수에서 서로 다른 ID 수를 뺀 값이다. 회차별 초기화 후 집계한다.
- 원시 기록은 각 회원의 SSE 데이터·수신 시각, DB 검증 행, DB 샘플, AI 호출·중복 통계와 k6 요약·로그다. metadata에는 SHA·조건·도구 해시·완료 여부를 남긴다. `summary.json`은 워밍업을 제외한 요약이며, 중단된 경우 완료 회차만 포함하므로 metadata의 `complete`와 회차 수를 함께 확인한다.
- p50/p95는 모든 회원 표본을 합쳐 선형 보간한다. N=1 본 측정 표본 20개의 p95 한계를 명시해야 한다. 처리량은 회차별 최초 accepted→최후 success 수신 구간의 합으로 계산한다.

최종 채택/기각, 전체 측정 조건 충족 여부와 기록 확정은 #313·#275의 사람 판정을 따른다. 소규모 예비 결과는 이슈에만 남기고 최종 성능 기록으로 커밋하지 않는다.

## 종료

```powershell
./perf/stop313.ps1
docker compose -f perf/compose.yaml stop mysql
```

종료 스크립트는 기록한 PID와 시작 시각이 모두 일치하는 Java 프로세스만 종료한다. DB 컨테이너와 원시 기록은 보존한다. 부모 체크아웃을 정리할 때도 필요한 로그·원시 결과를 먼저 보존한다.
