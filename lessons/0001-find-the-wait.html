추천 요청은 어디에서 기다릴까?

오늘의 목표: 가상 스레드 도입 전에 검증할 병목 가설 하나를 말한다.

코드에서 확인한 사실

RecommendationExecutorConfig는 플랫폼 스레드 4개와 대기열 8개를 설정한다. RecommendationServiceV2는 이 실행기에 작업을 제출하고, 그 작업에서 카카오 좌표 검색 → 후보 조회 → AI 추천 → 결과 저장을 진행한다. 카카오 검색은 HttpClient.send, AI 호출은 동기 RestClient.exchange를 사용한다.

아직 가설: 외부 응답을 기다리는 동안 실행 슬롯 4개가 차서, 다음 추천 작업의 시작이 지연될 수 있다. 코드 구조는 근거지만 실제 병목이라는 측정 결과는 아니다.

비동기와 가상 스레드를 구분하기

추천은 이미 요청 처리 흐름에서 작업을 넘기고 SSE로 결과를 보낸다. 이 비동기 구조에서도 백그라운드 플랫폼 스레드는 외부 응답을 기다릴 수 있다. 가상 스레드는 기다리는 작업을 적은 OS 스레드로 감당하는 선택지다. AI 계산 자체를 빠르게 만들지는 않는다. Oracle 공식 설명

첫 측정의 설계

처음에는 지연을 일정하게 제어하는 로컬 HTTP 대역으로 외부 API를 대신한다. 이는 외부 서비스 성능이 아닌 우리 실행 구조의 실험이다. 이후 실제 경로 측정으로 결과가 성립하는지 확인한다.

측정 구간알아낼 것
작업 제출 → 실행 시작실행 대기열 지연
외부 호출 시작 → 응답I/O 대기 시간
요청 시작 → SSE 최종 이벤트사용자가 기다린 전체 시간

서로 다른 회원으로 동시 작업 수를 1 → 4 → 8 → 16으로 올린다. 같은 회원은 중복 작업 방지에 걸린다. SSE 연결 성공만 세지 말고 성공·실패·거절·타임아웃과 완료 처리량, p95 지연, CPU와 메모리를 함께 센다. 워밍업과 반복으로 흔들림도 확인한다.

비교군은 A: 현재 4개 풀, B: 더 큰 플랫폼 스레드 풀, C: 작업당 가상 스레드다. B와 C는 같은 동시 실행 상한·대기/거절 정책·HTTP/DB 연결 한도에서 비교한다. 그래야 실행 수를 늘린 효과와 스레드 종류의 차이를 구분할 수 있다.

생각하고 펼쳐 보기

가상의 조건: 작업 8개가 동시에 도착하고, 작업마다 외부 응답을 2초 기다린다. 다른 비용은 무시한다. 현재 실행기에서 마지막 작업은 대략 언제 끝날까? 왜 그럴까?

생각한 뒤 해설 보기

약 4초다. 처음 4개가 2초 동안 실행 슬롯을 쓰고, 대기 중인 나머지 4개가 뒤이어 실행된다. 실제 측정값이 아니라 단순화한 예상이다. 슬롯을 8개로 늘린 플랫폼 풀에서도 약 2초가 될 수 있으므로, 이 결과만으로 가상 스레드의 고유한 이점을 주장할 수 없다.
